# Game Design Planner Runtime

Runtime modules for **playable prototypes** generated from a Game Design Planner plan. It holds only runtime code (no `UnityEditor`), so it goes into player builds. The editor-side import stays in the [planner bridge](../com.handsofhubris.planner-bridge/README.md).

Unity 2022.3 or later (Unity 6 included). Install it next to the bridge: *Window ▸ Package Manager ▸ + ▸ Add package from git URL…* with this folder's path, or `"com.handsofhubris.planner-runtime": "file:<path to this folder>"` in `Packages/manifest.json`.

When a plan asks for a playable prototype (Technical Architecture › Playable prototype), its export names the runtime version it needs, and the bridge refuses to import it into a project without that version, saying what to install.

## What is in 0.10.0

The lifecycle every module plugs into, and the first gameplay module: player movement with a third-person camera, placed in a scene the bridge builds from the plan, interaction (picking up the items placed on the map), the inventory shown on the plan's HUD, quests with typed goals and rewards, saving all of it — the first vertical slice — crafting, and a first, melee-only combat model. Interaction, inventory, quests and saving follow, each with its own PlayMode test (plans/UNITY_PLAYABLE_GAME_GENERATION_PLAN.md).

- **`PlannerPlayer.Create(position, settings)`**: a player with a CharacterController, **`PlannerMovement`** (the “movement” service; walks at the planned speed relative to the camera, turns to where it walks, gravity) and a **`PlannerThirdPersonCamera`** (planned distance and height behind the player).
- **`PlannerPlacement`** (0.3.0): an object placed from a location map of the plan — the player start, an item pickup (planner item ID, record key, count) or another spawn role — with the planner IDs of the map object and the location. The bridge's prototype scene puts one on each placement.
- **Interaction** (0.4.0): **`PlannerInteractor`** (the “interaction” service, after “movement”) targets the nearest usable **`IPlannerInteractable`** within its `Range` (the plan's Interaction range) of the player, measured on the ground plane, and uses it when the Interact action is pressed — once per press, and only while its runtime runs. `TargetChanged` reports the target for feedback; **`PlannerInteractionPrompt`** shows “[E] Pick up Brass Key” on screen (IMGUI, no UI asset needed).
- **`PlannerPickup`** (0.4.0): on an item placement, gives its item and amount once — **`PlannerItemAcquired`** (item ID, record key, count, source object) on the runtime's event bus — and disappears. A placement without an item or with a count below 1 is no target and logs a warning. Your own interactables implement `IPlannerInteractable` and add themselves to `PlannerInteractables` while enabled.
- **Inventory** (0.5.0): **`PlannerInventory`** (the “inventory” service) has the planned number of slots; each slot holds one item up to its planned stack size. Items are matched by planner ID. `TryAdd`/`TryRemove` are all-or-nothing: an unknown item, a count below 1 or not enough room changes nothing. `Changed` and **`PlannerInventoryChanged`** (event bus) report changes. As the **`IPlannerItemReceiver`** of the runtime it decides whether a pickup is taken: a full inventory leaves the item where it lies, and the prompt says “Inventory full”. Weight is not limited yet.
- **`PlannerHudBinding`** (0.5.0): binds the plan's HUD (the generated screen UXML on a `UIDocument`) to the inventory. The `bind-inventory` element (a Grid bound to the inventory in UI / UX › Screens) gets one cell per slot with the item's name and count, and each `bind-item-<item ID>` (a Counter bound to an item) shows how many the player has. Both update on every change.
- **Quests** (0.6.0): **`PlannerQuests`** (the “quests” service, after “inventory”) runs the plan's typed quest rules (goal: hold these items; reward: items, plus money and XP in the event). The plan's quest graph stays in charge through **`IPlannerQuestGraph`** — the export's generated `PlannerQuestGraph` over `PlannerQuestLog` — so a quest starts only when the graph allows it, and is recorded done there. Goals are checked when a quest starts and after every inventory change, never by name or text. The item reward goes into the inventory all or nothing (`PlannerInventory.TryAddAll`), exactly once; while it does not fit, the quest waits (`PlannerQuestRewardWaiting`). A quest the graph already had done is not rewarded again. Starting fails, with every reason, when the graph is missing or a rule names a quest or item the plan does not have. Events: `PlannerQuestStarted`, `PlannerQuestCompleted`. The HUD binding shows the quest tracker (`bind-quest`, `bind-quest-<quest ID>`).
- **Saving** (0.7.0): **`PlannerGameState`** captures and restores, as JSON, the state of the plan's saved parts that are linked to a runtime state (Save System › Saved parts › Runtime state): the player's position and facing; the inventory together with the map pickups already taken (saved as one, so a taken item never comes back); the quests with the quest graph's log and the rewards given. `Check` validates a part without changing anything — damaged JSON, unknown items or pickups, a count over the stack or more filled slots than planned throw **`PlannerStateException`** — and `BeginRestore`/`EndRestore` pause the quests so loading never rewards a quest again. The game's save system (**`IPlannerSaveSystem`**) is the export's generated PlannerSaveSlice over the generated PlannerSave (planned version, slots, migrations), which checks every part before it restores any.
- **Crafting** (0.9.0): **`PlannerCrafting`** (the “crafting” service) crafts the plan's recipes — item inputs, one output, the quests that unlock it — in the inventory, all or nothing (`PlannerInventory.TryExchange`): when an input is missing, the recipe is locked or the output does not fit, nothing changes, and `CanCraft` says which. Its only state is the inventory's, so a saved game stays consistent by itself. **`PlannerCraftingPanel`** (IMGUI) is opened with the planned crafting control (`IPlannerMenuSource`; the Input System source's Crafting action) and shows each recipe with have/need and a Craft button.
- **Combat** (0.10.0), the first supported model only — melee: **`PlannerCombat`** (the “combat” service) lets the player hit the nearest living enemy in reach on the Attack action, at the Player weapon's attacks per second, for the plan's damage formula (**`IPlannerDamageFormula`**, the export's generated PlannerDamageFormula; attack, armor, resist, crit = 1). **`PlannerEnemy`** (with **`PlannerHealth`**) has the planned HP, damage, rate, armor, resistances, speed and aggression: unless passive it chases the player within the aggro radius and hits in reach. A defeated enemy publishes its XP (`PlannerEnemyDefeated`) and holds its guaranteed loot (**`PlannerLoot`**, taken once by interacting); a defeated player is back at the start with full health (`PlannerPlayerDefeated`). Saved as `PlannerStateKind.Combat`; the HUD's Health stat bar shows the player's health. Ranged, caster and support enemies, crits, status effects and difficulty scaling are not part of it.
- **Self-test** (0.8.0): **`PlannerSelfTest`** checks a built player started with `-hohSelfTest` (runtime, missing scripts, pickups, quests, crafting, save and load into a fresh game) and quits with 0 or 1; `-hohSelfTestReport <file>` writes a JSON report.
- **`IPlannerMoveSource`**: where movement input comes from. **`PlannerInputSystemSource`** (assembly `HoHPlanner.Runtime.InputSystem`, compiled only when the Input System package is installed) reads the Move and Interact actions of the generated `.inputactions` asset.

The lifecycle:

- **`IPlannerService`** — one runtime module: an `Id`, the ids it `DependsOn`, `Initialize(runtime)` and `Shutdown()`.
- **`PlannerRuntime`** — starts services after their dependencies and stops them in reverse. Before starting anything it checks for missing required modules, unknown dependencies, duplicate ids and cycles, and reports all of them at once. A service that throws while starting rolls back the ones already started. Stopping continues past a service that throws and lists it in `Errors`.
- **`PlannerEvents`** — a typed event bus per runtime (`Subscribe<T>`, `Publish<T>`); a failing handler is reported and does not stop the others.
- **`PlannerRuntimeHost`** — the scene component: registers every `IPlannerService` component on its object and children, starts them on `Start`, stops them on destroy or quit, and logs one clear error when the plan's required modules are missing.
- **`PlannerEnvironment`** — whether the Input System and URP are installed *and active* (compile-time defines and the active render pipeline), with the place to fix each.

## Tests

`Tests/Editor` (EditMode: lifecycle contract, events, environment, version) and `Tests/Runtime` (PlayMode: the host in a running scene). List the package under `"testables"` in the project's `Packages/manifest.json` to run them.
